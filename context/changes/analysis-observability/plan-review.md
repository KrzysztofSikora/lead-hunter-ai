## Decisions the PR reviewer should look at
- D-3: storing a cancel as `FAILED` with error `cancelled` instead of a `CANCELLED` status. This is a persisted value. It also uses a daily slot and counts as a failure in job-run statistics (finding 3).
- D-1: moving retries from the SDK to the runner changes analysis retry timing. A `Retry-After` above 30 s now gives up, where the SDK waited up to its own limit.
- D-5: idempotent `POST /api/analysis/cancel` that always pauses. This is a public API shape.

## What is good
- The Findings are grounded and I confirmed them in the code: the `service.ts` line ranges, `TIMEOUT_MS`/`MAX_RETRIES` in `create-provider.ts:8-10`, the `signal?: AbortSignal` request option in both SDK versions, `APIUserAbortError` exported by both SDKs, `app_meta` unused by code, the deny-by-default hook in `auth/routes.ts:54-62`, and the `AnalysisLine` and routes locations in the web app.
- A closed reason-code enum (D-8) makes AC2 leak-proof by construction, instead of relying on scrubbing `analyses.error` strings.
- Persisting the paused flag (D-4) follows AC3 and the overheating-Pi scenario. It needs no migration.
- The retry policy mirrors `rss/retry.ts`. It is a pure helper in the module and respects the ESLint layer rule. `retry-policy.ts` and `activity.ts` are good mutation targets.
- The scope is tight. Offer drafts keep their SDK retries, nothing stops Ollama, and no new e2e or component tests are added, which respects the test budget.
- The human checks on the Pi are concrete and match the roadmap's acceptance (visible run, cancel, paused across restart, temperature and load, Ollama behaviour).
