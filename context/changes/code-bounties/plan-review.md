| 1 | major | Failure paths / AC2 | Closed or missing Opire rewards are never remembered, so they get checked again on every run and can take the whole 20-check cap. The service adds to the cursor only the keys of items it ingested: `remembered.push(item.key)` runs inside the item loop (`apps/api/src/modules/sources/service.ts:253`), and a closed reward is not an item. D-8 says "skips `closed`, 404 and 410" and promises that "rewards beyond the cap … come next run". With 20 or more closed rewards ahead of a new open one in Opire's array (the DEV write-up the plan cites says closed issues are common), every run spends its 20 checks on the same closed issues and the open one is never reached. The Phase 4 test "25 new rewards → 20 checks … the next run checks the other 5" passes only if the first 20 are open. | Remember the checked-and-skipped keys: add an outcome field such as `checkedKeys: string[]` that the service merges into the cursor, or remember skipped keys in the adapter's own cursor. Add a test with 25 closed rewards followed by 1 open one: the open one is stored within two runs, with exact request counts. Re-checking a closed issue later is already a [FOLLOW-UP]. |
| 2 | major | Failure paths / AC2 | Most Opire signals may be rejected as `too_old` before anyone sees them. The same risk applies to GitHub search results that are older than 30 days. The plan doesn't mention it, and no test covers it. | Decide it in a Decisions row. For example, Opire `publishedAt` = the reward's own creation date if Opire has one, else `null` (the `too_old` rule skips `null`), or the fetch time. Add an integration test in which an open issue created 90 days ago with an active reward reaches analysis, not `too_old`. |

## Decisions the PR reviewer should look at
- D-8: the Opire source makes GitHub core-API calls, possibly with the token. Closed rewards are re-checked every run (finding 1), and the issue's `created_at` drives `too_old` (finding 2).
- D-10: for bounty sources, the parser's reward replaces even a model budget that passed the guard. Together with D-7's narrow keyword list, this can hide amounts that the issue states.
- D-12: GitHub search first means the Opire reward is lost and the signal is downgraded from `DIRECT_REQUEST`. This depends on run order, and the fix is deferred as a [FOLLOW-UP].
- D-9: the token is sent on same-origin redirects (a security choice).
- D-1/D-2: a merge with S-18 (`change/public-tenders`, which also adds `resumeFrom` and migration `0012`) is certain.

## What is good
- The findings are grounded. Every cited `file:line` checked out (`ports.ts`, `service.ts:226`, `compose.ts`, `output-guard.ts:85-113`, `cues.ts`, `prefilter.ts:118`, `server.ts:90`, `strings.pl.ts:343`), and the S-18 shapes match `git diff main change/public-tenders`.
- The reward comes from a deterministic parser and the API, not from the model. Ambiguity stays `null`, which fits PRD §0 and §7.
- The token handling is careful: the redaction key `token`, the header dropped on cross-origin hops, a canary across the logs, the API, the DB and the Opire request, and both switch states tested.
- The rate-limit tests assert exact request counts and the spacing with an injected clock, and the reset time is bounded (lessons applied).
- The scope is tight, and the out-of-scope items are explicit and recorded as [FOLLOW-UP].
