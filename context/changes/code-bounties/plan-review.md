## Decisions the PR reviewer should look at
- D-10: whether a `paid` label (finding 1) or a bare `bounty` label is enough for `DIRECT_REQUEST`.
- D-8: one GitHub check per Opire reward, the 20-check cap, and failed checks that are not remembered.
- D-5: how GitHub rate-limit answers are read; this rests on unverified research.
- D-2: the new `raw_signals.bounty_json` column.
- D-9: custom headers on the shared guarded client, and stripping them on a cross-origin hop.

## What is good
- The cited code was checked against `main`: ports, `service.ts` (cursor, `checkTender`, `parseConfigUrl`, the `create`/`update` tender paths), the client's `GetOptions`, the logger's redaction keys, the guard and cue lines, the pre-filter rules and the migration number. All of it is accurate.
- The plan carries the earlier attempt's review findings over explicitly. The cursor-progress lesson is tested with "25 closed rewards then 1 open". The look-alike lesson gets a concrete negative list. The both-orders test answers the shared-record lesson.
- Truth first: rewards come from a deterministic parser and stay `null` when ambiguous. `publishedAt` is `null` rather than invented. The fixtures are synthetic and labelled, with a `[REVIEW]` deviation for the recorded responses.
- The token is handled with care: the `token` key is covered by redaction, the header is dropped on an origin change, Opire never gets it, and a canary test covers both.
- The Phase 3 checkpoint is well placed before Opire builds on the unverified GitHub behaviour.
