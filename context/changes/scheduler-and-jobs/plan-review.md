# Plan review: scheduler-and-jobs

Verdict: NEEDS CHANGES

| # | Severity | Check | Finding | Suggested change |
|---|----------|-------|---------|------------------|
| 1 | blocker | Design / Failure paths (FR-17 AC2) | D-2 makes a lock stale when "`owner_host` equals `os.hostname()` and … `owner_pid === process.pid`", and says "`acquire` also takes over a stale lock". In the running server, its own live cycle holds the lock with its own pid, so a second `POST /api/jobs/discover`, a scheduler slot or `POST /api/sources/:id/run` from the same process sees the lock as stale, takes it over, and (D-3) marks the live cycle's rows `interrupted`. That is exactly the double run AC2 forbids. The D-15 busy tests only catch it if they use the real pid. | Apply the own-pid rule only in `releaseStale()` at start, before this process has acquired anything. Alternatively, have `acquire` treat a lock whose `owner_token` this process minted (an in-memory set) as held. Add an integration case where the cycle and the second start run in one process with `pid: process.pid`, and expect `busy`. |
| 2 | major | Failure paths (D-3, *Error model*) | Shutdown "marks the process's own running rows `interrupted` and releases the lock", but the port only has `interruptRunning(at): number`, which has no owner filter. If the CLI holds the lock (`docker compose exec app pnpm discover`) when the server gets SIGTERM, the server marks the CLI's live rows `interrupted`. The ordering is also open: after the release, the background `done` keeps running until `process.exit`. It can then overwrite `interrupted` with `ok` via `finishRun`, and a request that is still accepted can start a new cycle before `app.close()`. | Interrupt rows only when this process holds the lock (`handle` is present), inside the same transaction as the release, keyed on its token. Use this order: stop the schedule, `app.close()`, then interrupt and release, then exit. Make `finishRun`/`finishCycle` update only `WHERE status = 'running'`, so an `interrupted` row is never rewritten. |
| 3 | major | Agent decisions (autonomy §2) | Several decisions marked `cheap` are `costly` by the policy. D-3 rewrites persisted rows (`running` → `failed/interrupted`). D-4 adds a `409 busy` to the public `POST /api/sources/:id/run`. D-12 adds the public route `POST /api/opportunities/:id/analyze`. D-13 fixes the user-facing label for FR-17 AC4. That AC says "When they press **"Uruchom teraz"** … Then one cycle runs", but the plan gives the cycle the label **Uruchom wszystkie teraz** and keeps "Uruchom teraz" for a single source. | Re-mark D-3, D-4, D-12 and D-13 as `costly` so they appear under *Decisions to confirm*. For D-13, state the AC4 wording gap explicitly (the PRD names "Uruchom teraz" for a cycle) and pick the option that keeps doors open. Keep the strings in `strings.pl.ts` only, so a rename touches one line. |
| 4 | major | Truth first (D-8) | `rejected` = "pre-filter rule set". The `no_text` rule does not reject: `moveFor` in `apps/api/src/modules/analysis/service.ts` sends it to `NEEDS_VERIFICATION`, and every other rule goes to `REJECTED`. The run would report rows that wait for verification as rejected. | Count `rejected` as `prefilter_rule IS NOT NULL AND prefilter_rule <> 'no_text'` (or reuse the same mapping). Add a `no_text` signal to the Phase 3 counter test. |
| 5 | minor | Failure paths (*Error model*) | "A heartbeat that finds the lock lost … The run finishes and records normally". A takeover only happens after more than 2 minutes without a heartbeat (for example a blocked event loop, see the url-import-guard lesson). By then the new owner has marked these rows `interrupted` (D-3), and the old run keeps fetching alongside the new owner. | When `heartbeat()` returns false, stop before the next source and do not overwrite rows (covered by the `WHERE status='running'` guard from #2). |
| 6 | minor | Design (D-5) | The slot is "the UTC ms of the croner fire time, rounded down to the minute". If you take that from the wall clock, a timer that fires a few ms early rounds to 07:59, which is a different slot key. | Take the instant from croner's scheduled time (`job.currentRun()`/the planned `nextRun` captured before the fire), or round to the nearest minute. Test one early fire. |
| 7 | minor | Phasing / TR-20 | Migration `0008` alters `job_runs` and `raw_signals`, which hold rows from S-10. TR-20 asks for "migration test from each previous schema version with seeded rows" (`context/test-plan.md:55`). The plan relies only on the existing tests (*Risks*, last bullet), and `apps/api/test/db.int.test.ts` has no seeded-upgrade case. | In Phase 1, add one case: seed a `job_runs` row and a `raw_signals` row at 0007, migrate, and assert `trigger/parent_run_id/scheduled_for` are null, `skipped` is 0, and `job_run_id` is null. |
| 8 | minor | Scope / lesson (config comments) | *Risks* says the 2-minute CLI case is "Documented in `.env.example`'s comment and the README line for `pnpm discover`", but no phase lists the README in *Files*. | Add the README (or `CLAUDE.md` command row) to the Phase 2 files, or drop the claim. |

## Decisions the PR reviewer should look at
- D-2: staleness rules (own-pid shortcut, 2-minute heartbeat); finding #1 depends on this.
- D-5: unique `scheduled_for` as the slot idempotency key (data shape).
- D-8: read-time counters through `raw_signals.job_run_id` (data shape, and the definition of `rejected`).
- D-10: async `202` cycle and the `JobRun`/`JobList` contract (public API).
- D-13: "Uruchom wszystkie teraz" against the FR-17 AC4 wording "Uruchom teraz".

## What is good
- Every cited symbol and line checked is real and close to where the plan says. I checked `job_runs` in `schema.ts`, `SourceService.run`/`runEnabled`, `startRun`, the `setInterval` in `server.ts`, the `waiting` predicate in `analysis-repository.ts`, the mock usage at `mock.ts:102`, and the list query shape. croner 10.0.1 exists (MIT), and `timezone`, `protect`, `catch`, `unref` and `nextRuns` match its README and `.d.ts`.
- Rejecting the 02:xx hour in D-6 matches both Warsaw DST transitions, so it removes the gap/overlap problem for every valid config instead of relying on library behaviour.
- D-7, which keeps LLM spend in one process, settles the overlap risk that analysis-and-scoring raised. The two-step lesson is honoured with an explicit takeover-then-late-release test.
- The phases are ordered by dependency, each one runs the Gates commands, and the human checks are concrete. Out of scope matches the roadmap's *Decided up front* (no catch-up).
