# Plan review: pi-deployment

Verdict: READY WITH NOTES

| # | Severity | Check | Finding | Suggested change |

| 1 | major | Grounding / Failure paths | The crash human check uses `docker kill -s KILL <app container>` and expects "the container comes back by itself" (plan l.244-246). Docker treats `kill` as a manual stop: `daemon/kill.go:95-96` sets `container.HasBeenManuallyStopped = true` (moby master), and the docs say a manually stopped container's restart policy is ignored (https://docs.docker.com/engine/containers/start-containers-automatically/). With `unless-stopped` the container stays down, so the check would fail (or the restart part of FR-23 AC1 would be recorded wrongly). | Kill the server process instead, not the container: e.g. `docker compose exec app sh -c 'kill -9 $(pgrep -f dist/server.js)'`, or `sudo kill -9 <host pid of node>` taken from `docker top`. Under `init: true` tini then exits non-zero and the restart policy applies. Change the README/human-check wording to match. |
| 2 | major | Design / Grounding | The seed CLI's analysis runner needs a `ProfileReader`, and the plan does not say where one comes from (Design l.124). `createProfileService().get()` throws `operator profile row is missing` (`apps/api/src/modules/profile/service.ts:26-27`). Only the profile routes create that row (`profile/routes.ts:14`, `ensureExample()`). The Phase 1 agent check runs the seed on a fresh `mktemp -d`, where no server has started. There `runPrefilter` (`analysis/service.ts:62-64`, outside any try) throws, so the drain rejects and nothing gets analysed. If the call is moved inside a try, every analysis is saved as `FAILED internal_error` instead. In both cases the timing evidence then measures unscored rows, and `minScore=65` returns nothing. The "przeanalizowano M" line does not reveal this clearly. | In Design, have the seed call `createProfileService(...).ensureExample()` before the runner and read the profile with `profile: { get: () => service.get().profile }`, as `server.ts:76` does. In the agent check, require M = N and the number of COMPLETE analyses = N (or print the FAILED count and exit 1 if it is above 0). |
| 3 | minor | Design | In `perf`, the seed runs through `docker exec` while the perf server is already running with `LLM_PROVIDER=mock` (l.134-137). That writes duplicate `analyses` rows. Both runners also share `countSince`, so the seed can stop up to 20 short (default limit 20, `env.ts:170`). | Seed first with `docker run --rm -v lead-hunter-perf:/data ... node apps/api/dist/cli/seed-demo.js`, then start the perf server. ## Decisions the PR reviewer should look at
- D-1: `synchronous = FULL` changes fsync behaviour for every connection on an SD card. It is cheap to revert, but the Pi write-latency evidence should be read.
- D-5: the container smoke runs for the first time in CI (no Docker in the sandbox). Read the CI log of the `image` job.
- D-2: the seed CLI writes to whatever `DATA_DIR` points at. Its only safety is the empty-DB refusal, so confirm it is never documented against `./data`.

## What is good
- The findings are grounded: every cited file and line checked out (`client.ts`, `server.ts:47-63/191-203`, `ingest.ts:36`, `ports.ts:62`, `analysis/service.ts:59`, `env.ts:66`, `auth/routes.ts:24`, `env.test.ts:208`, `e2e/env.ts`, `defines.gypi:16`), as did the routes `/api/auth/login`, `/api/signals/import`, `/api/digest/today` and `minScore`, and the health `db.migrations` field.
- The NFR-04 analysis (WAL + NORMAL can lose committed transactions) is correct, and the fix is one line.
- The smoke uses `docker run` with no `.env`, respects the lesson that a gate run must not rewrite committed files, and cleans up after itself.
- The scope is tight: systemd, arm64 CI, S-15 backup and S-05 Ollama use stay out, and the README does not claim the app already uses Ollama.
- Every human check on the Pi is concrete and names its evidence location.
