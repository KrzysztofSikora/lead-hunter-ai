# Plan: operator-profile (S-02)

## Goal and end state
The operator has one profile (skills, preferences, constraints, goals) that is stored in SQLite,
read and replaced through `GET`/`PUT /api/profile`, and edited in a Polish *Profil* view. Later
slices (pre-filter, scoring, offer drafts) read it through the profile service; this item only
provides that reader.

Observable when done:
- FR-01 AC1: on a fresh database the first start stores an anonymous example profile; `GET
  /api/profile` returns it with `example: true` and the view shows the label `PRZYKŁAD`. The
  operator edits and saves it in the UI; afterwards `example: false` and the label is gone.
- FR-01 AC2: a saved profile is returned unchanged by `GET /api/profile` after the app is built
  again on the same database file (restart).
- FR-01 AC3: a payload with an unknown field (top-level or nested), a negative amount, or an
  effort split not summing to 100 gets 400 `{ error: "validation_failed", fields: [...] }` with
  the field path, and the stored profile is unchanged.
- FR-01 AC4: the example profile contains no names, rates, amounts or clients (asserted by a
  test); the repository contains no real profile (a human check greps for it).
- FR-25 AC1 (pattern): every route's body validation error now has the same field-level shape.

## Scope
- In: `OperatorProfile` contract (Zod) and DTOs; `operator_profile` table and migration;
  repository; profile module (service, example profile, routes); a field-level 400 error shape
  for all routes; seeding on first start; react-router with a nav (start view + *Profil*); the
  profile form; e2e smoke extended with a profile edit; README *Co działa*.
- Out: consumers of the profile (pre-filter S-04, scoring S-04, offer drafts S-07); scoring
  filters of FR-10 AC6 that are not FR-01 fields (minimum score, maximum source age); LLM and
  schedule settings shown on *Profile & Settings* in brief §11 (S-05, S-12); profile export
  (S-15); edit history or optimistic concurrency (one operator, one device at a time, A-04);
  TanStack Query (D-8).

## Findings
- Schema has `app_meta` and `sessions` only (`apps/api/src/infrastructure/db/schema.ts:3-12`);
  migrations are generated by drizzle-kit into `apps/api/migrations/` (`0000_*`, `0001_*`) and
  applied at start (`apps/api/src/server.ts:37`, `infrastructure/db/migrate.ts:8`).
- Module pattern from S-01: `modules/auth/{ports,service,routes}.ts`; `routes.ts` is the only
  module file allowed to import Fastify, modules reach drivers only through ports
  (`eslint.config.js:45-64`); repositories live in `infrastructure/db/*-repository.ts` and are
  wired in `server.ts:45-55` and in the test helper (`apps/api/test/helpers/app.ts:65-80`).
  `AppDeps` (`apps/api/src/app.ts:14`) is the injection point.
- Every matched `/api/*` route is protected by the deny-by-default guard
  (`modules/auth/routes.ts:55-63`); the auth test walks the route table
  (`apps/api/test/auth.int.test.ts:26`) and the OpenAPI test compares documented and registered
  routes (`apps/api/test/openapi.int.test.ts:9`), so the new routes are covered by both without
  changes.
- Validation errors today use Fastify's default body (`{ statusCode, code: "FST_ERR_VALIDATION",
  error, message }`, one string); no test or UI code depends on the 400 body (grep for `400` in
  `apps/`, `e2e/`). fastify-type-provider-zod 7.0.0 puts the Zod issues on `error.validation`
  as `{ keyword: issue.code, instancePath: "/a/0/b", message, params: { ...rest of issue } }`
  and exports `hasZodFastifySchemaValidationErrors(error)` (`dist/esm/errors.js:22-45`). For a
  strict object, Zod 4 reports one `unrecognized_keys` issue at the parent path with
  `params.keys`.
- Fastify passes an error thrown from a child context's error handler to the parent's handler,
  so the auth scope's handler (`modules/auth/routes.ts:68-75`, rethrows non-throttle errors)
  keeps working under a root handler.
- Web: no router (`apps/web/src/App.tsx`, S-01 D-10 deferred routing "until there are views");
  all calls go through `apiFetch` (`apps/web/src/api/client.ts:17`) so a 401 shows the login
  form. Non-`/api` GETs fall back to `index.html` (`apps/api/src/app.ts:62-70`), so a deep link
  to `/profil` works in production.
- react-router 8.5.0 (tech-stack): peer `react >=19.2.7` (we have 19.3.1), engines
  `node >=22.22.0`; dependencies `cookie-es`, `@remix-run/route-pattern` (`npm view`,
  2026-10-25). Declarative mode (`BrowserRouter`, `Routes`, `Route`, `NavLink`) per tech-stack;
  confirm the export names against the installed package in Phase 2.
- e2e: Playwright starts the built server once per run on a fresh temp `DATA_DIR`
  (`playwright.config.ts:8`), so the example profile is present at the start of every run. The
  budget allows at most 2 spec files; the profile check goes into `e2e/smoke.spec.ts` as a
  second test.
- Test budget (`context/test-plan.md`): no `test` risk names FR-01, so the item gets one
  integration test file for its API main path and validation, and no component tests.

## Decisions
| ID | Question | Chosen | Alternatives (and what they would buy) | Why | Reversal | Decided by |
|----|----------|--------|----------------------------------------|-----|----------|------------|
| D-1 | How the profile is stored | One row in `operator_profile(id INTEGER PK CHECK (id = 1), schema_version INTEGER, data TEXT JSON, is_example INTEGER 0/1, updated_at INTEGER epoch ms UTC)`; `data` is the whole `OperatorProfile`, validated by the shared Zod schema on write and on read | B: one column per field and child tables for lists (SQL-queryable, but every new field is a migration); C: brief §14's six JSON group columns (closer to the brief, but the grouping buys nothing and splits validation) | The profile is read whole by every consumer and written whole by one form; new fields stay additive inside the document with `schema_version` | costly (persisted data shape, migration) | agent |
| D-2 | Profile field shape | As in *Design* `OperatorProfile`: lists of trimmed tags; `experience` free text; enums for billing models and work modes; ISO codes for languages/countries; `Money { amountMinor, currency }` per amount (PLN/EUR/USD, as payments); `rateRanges[]` with unit and min ≤ max; `minimumJobValue` and `monthlyRevenueGoal` nullable; `effortSplit` default 80/20. All objects strict | B: one profile currency for all amounts (simpler form, but rates for Polish and international clients differ in currency); C: free-text fields for billing, work mode and languages (no enums to maintain, but the pre-filter cannot match them deterministically) | Deterministic consumers (pre-filter, scoring) need codes and enums; per-amount currency keeps the door open | costly (API contract, persisted shape) | agent |
| D-3 | Example profile and `PRZYKŁAD` label | The example is a constant in `modules/profile/example.ts` (generic §2.1 skills, no names, rates, amounts or clients; money fields `null`/empty). `ensureExample()` inserts it with `is_example = 1` only when no row exists, called when the profile routes are registered (both the server and the test helper build the app). Any successful `PUT` stores `is_example = 0`, even if the values are unchanged. The API returns `example: boolean`; the UI shows `PRZYKŁAD` while it is true | B: no row; `GET` returns the constant until the first save (no write at start, but contradicts "seeded on first start"); C: label decided by comparing with the constant (no flag, but a save of unchanged values would still look like the example) | Roadmap *Decided up front* says seeded on first start; an explicit save is the operator's confirmation | cheap | user (roadmap S-02) + agent |
| D-4 | API contract | `GET /api/profile` → 200 `ProfileResponse { profile, example, updatedAt }`; `PUT /api/profile` body `OperatorProfile` (full replace) → 200 `ProfileResponse`; 400 `ValidationError`. No `PATCH`, no id in the path | B: `PATCH` with partial updates (smaller payloads, but partial validation of the split and ranges gets awkward); C: `POST /api/profile` | One record (A-04); the form always sends the whole profile, so replace is the simplest correct contract | costly (public API) | agent |
| D-5 | Field-level validation error shape | A root error handler in `buildApp` maps Zod validation errors on any route to 400 `{ error: "validation_failed", fields: [{ path, code, message }] }`; `path` is dot-joined (`rateRanges.0.maxMinor`), an `unrecognized_keys` issue becomes one entry per unknown key (`path` = parent path + key, `code` `unrecognized_keys`). Other errors keep Fastify's default handling | B: handle it only in the profile routes (no change to login's 400, but FR-25 AC1 wants one shape everywhere); C: return Zod's `flattenError` (`{ formErrors, fieldErrors }`, a standard, but loses nested paths and unknown-key names) | One shape for every later form; nested paths let the UI place errors | costly (public API) | agent |
| D-6 | Wording of field errors in the UI | The UI shows Polish text from `strings.pl.ts` chosen by `code` (`too_small`, `too_big`, `invalid_type`, `invalid_format`, …) with a generic fallback; the schema's custom refinements (split ≠ 100, min > max) carry Polish messages that the UI shows as is. The form runs the same Zod schema before sending, so the server error is a backstop | B: Polish messages for every rule inside `packages/contracts` (one source, but contracts become UI copy); C: show Zod's English messages (no mapping, but breaks D-11 Polish UI) | Keeps D-11 (strings in one module) and contracts language-neutral except two domain rules | cheap | agent |
| D-7 | Money input in the form | Whole currency units in the form (`1500` PLN), converted to minor units by integer multiplication (`× 100`) on send and back by integer division on load; the API stays in minor units | B: decimal input (`1500,50`) parsed as a string into minor units (exact grosze, more parsing code); C: minor units in the form (no conversion, unusable) | Preferences are whole-unit numbers in practice; no float arithmetic | cheap | agent |
| D-8 | Routing and data fetching in the web app | Add `react-router` 8.5.0 (tech-stack) now, declarative mode: `/` (current status view) and `/profil`, a nav with *Start* and *Profil*; the profile uses plain `apiFetch` with local state; TanStack Query waits for the first list (S-03) | B: view state without a router (no dependency, but no deep link to *Profil* and S-03 would add the router anyway); C: also TanStack Query now (tech-stack has it, but one GET does not need a cache) | Tech-stack already chose the router; the second view is where S-01 D-10 said routing would start | costly (new runtime dependency, plan-review 2) | agent (tech-stack) |
| D-9 | List fields in the form | One textarea per tag list, one item per line; the form trims, drops empty lines and case-insensitive duplicates before sending. Rate ranges are rows with add/remove buttons | B: chip/tag input components (nicer, more code, no component library per tech-stack); C: comma-separated text inputs (shorter, but tags may contain commas, e.g. "B2B, kontrakty") | Least UI code, no ambiguity, works on a phone | cheap | agent |
| D-10 | Where the profile reader for later slices lives | `createProfileService(deps)` exposes `get(): StoredProfile` (and `save`, `ensureExample`); later slices receive this service (or a `ProfileReader` port with `get()`) through deps | B: later slices query the repository directly (one hop less, but bypasses the read-side schema check) | One place validates stored JSON | cheap | agent |

## Design

### Contract (`packages/contracts/src/profile.ts`)
```
Tag            = string, trimmed, 1–80 chars
TagList        = Tag[] (max 100)
Currency       = 'PLN' | 'EUR' | 'USD'
Money          = strict { amountMinor: int, 0 ≤ n ≤ 100_000_000_000, currency }
RateRange      = strict { unit: 'HOUR' | 'DAY' | 'PROJECT', currency, minMinor: int ≥ 0, maxMinor: int ≥ 0 }
                 refine minMinor ≤ maxMinor, path ['maxMinor'], message 'górna granica mniejsza niż dolna'
EffortSplit    = strict { directRevenuePercent: int 0–100, productHypothesisPercent: int 0–100 }
                 refine sum = 100, path [] (the split object), message 'suma musi wynosić 100'
OperatorProfile = strict {
  skills: TagList, experience: string (0–4000), serviceTypes: TagList,
  preferredTechnologies: TagList, excludedTechnologies: TagList,
  industries: TagList, excludedCategories: TagList,
  minimumJobValue: Money | null,
  billingModels: ('FIXED_PRICE' | 'HOURLY' | 'DAILY' | 'RETAINER')[] (unique, may be empty = no preference),
  languages: string /^[a-z]{2}$/ [] (1–10, ISO 639-1),
  workModes: ('REMOTE' | 'HYBRID' | 'ONSITE')[] (1–3, unique),
  countries: string /^[A-Z]{2}$/ [] (0–50, ISO 3166-1 alpha-2; empty = any),
  weeklyHours: int 0–168,
  rateRanges: RateRange[] (max 10),
  monthlyRevenueGoal: Money | null,
  effortSplit: EffortSplit,
}
ProfileResponse = strict { profile: OperatorProfile, example: boolean, updatedAt: string (ISO 8601 UTC) }
ValidationError = strict { error: 'validation_failed', fields: { path: string, code: string, message: string }[] }
```
Exported from `packages/contracts/src/index.ts`. Uniqueness of enum lists is a `refine` on the
array.

### Data (`apps/api/migrations/0002_*`)
`operator_profile` as in D-1. Drizzle `check('single_row', sql\`id = 1\`)`; if drizzle-kit
0.31 does not emit it, the repository always writes `id = 1` and the deviation is logged.

### Profile module (`apps/api/src/modules/profile/`)
- `ports.ts`: `ProfileRepository { get(): StoredRow | undefined; insertIfMissing(row): void;
  upsert(row): void }` with `StoredRow { data: unknown; isExample: boolean; updatedAt: number;
  schemaVersion: number }`. `Clock` (`now(): Date`) moves to `apps/api/src/modules/shared/clock.ts`
  and `modules/auth/ports.ts` re-exports it: S-01 D-12 kept it in auth until a second user
  appeared, and this module is that user.
- `example.ts`: `EXAMPLE_PROFILE: OperatorProfile`, generic skills from brief §2.1 (e.g.
  TypeScript, Node.js, React, integracje API, automatyzacje, aplikacje z LLM, Raspberry Pi,
  ESP32, LoRa, IoT, druk 3D, prototypowanie), service types (aplikacje webowe, integracje,
  prototypy IoT), languages `pl`, `en`, countries `PL`, work modes `REMOTE`, `weeklyHours` 20,
  billing `FIXED_PRICE`, `HOURLY`, no rate ranges, `minimumJobValue` and
  `monthlyRevenueGoal` `null`, split 80/20. A file comment says it is a DEMO example (PRD
  §16.1).
- `service.ts` `createProfileService({ repository, clock })`:
  - `ensureExample()`: `insertIfMissing({ data: EXAMPLE_PROFILE, isExample: true, … })`.
  - `get(): { profile, example, updatedAt: Date }`: reads the row and parses `data` with
    `OperatorProfile`; a missing row or a failed parse throws (both are bugs after
    `ensureExample`, surfaced as 500).
  - `save(profile: OperatorProfile)`: upserts with `isExample: false`, `updatedAt = clock.now()`,
    `schemaVersion = PROFILE_SCHEMA_VERSION` (1); returns `get()`.
- `routes.ts` `registerProfileRoutes(app, deps)`: calls `ensureExample()`, registers the two
  routes of D-4 with Zod schemas (`body: OperatorProfile`, `response: { 200: ProfileResponse,
  400: ValidationError }`).

### Error model
| Case | Status | Body |
|------|--------|------|
| no session | 401 | `{ error: "unauthorized" }` (existing guard) |
| invalid body on any route | 400 | `ValidationError` (D-5) |
| stored profile unreadable | 500 | Fastify default (logged) |

### Web (`apps/web/src/`)
`main.tsx` wraps `App` in `BrowserRouter`; `App` keeps the S-01 view states and, when `ready`,
renders a nav and `Routes` (`/` → current status shell, `/profil` → `ProfilePage`, anything
else → `/`). `ProfilePage` loads `GET /api/profile`, shows `PRZYKŁAD` (text label, not only
colour, NFR-07) while `example`, renders the sections *Kompetencje*, *Preferencje*,
*Ograniczenia*, *Stawki i cele*, validates with `OperatorProfile.safeParse` before `PUT`, shows
field errors next to their inputs (`aria-describedby`), and a status line `Zapisano` /
`Nie udało się zapisać`.

## Risks and unknowns

  against the installed package; Phase 2 confirms them, a different API is a `[minor]`
  deviation.

  stored JSON on read.
