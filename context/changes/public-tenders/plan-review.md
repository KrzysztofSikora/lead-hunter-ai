| 1 | major | Failure paths | A truncated window loses notices for good. D-9 marks a run that hits the page cap as `partial`. The next run then asks only for `lastSuccessAt − 24 h`. Notices past the cap in the old window are never fetched again. ## Decisions the PR reviewer should look at
- D-3: adds `PUBLIC_TENDER` to the PRD's evidence-level axis (§5.4), so that axis now also encodes a channel.
- D-9: the window, page cap and truncation behaviour (finding 1); this decides whether notices are lost.
- D-13: sends every CPV-matched notice to the paid LLM (finding 5).
- D-2: a tender-only column vs a typed metadata column, before S-19 (finding 14).
- D-18: reads every BZP 403 as `rate_limited`, which would hide a real access block behind a one-hour wait.

## What is good
- The findings are grounded precisely: every cited `file:line` I checked matches the code (`ports.ts:24-39`, `source-repository.ts:12,57`, `service.ts:230`, `prefilter.ts:117-119`, `rubric.ts:18-25`, `score.ts:18-23`, `select.ts:39-44`, `output-guard.ts:85-113`).
- The plan is honest about what the planning session could not verify (proxy refusals). It confines every API field read to one `map-notice.ts`/`query.ts` per adapter and puts a checkpoint on the first real run.
- The design is deterministic where the PRD asks for it: the evidence level and `sourceBudget` come from the source type and the tender facts, never from the model (D-3, D-6).
- It applies the binding lessons explicitly: bounded dates, a linear HTML pass with a test at maximum size, validation before storing, and an off-state filter test.
- It reuses the existing lock, cursor, run history and explicit-error model, and every outbound request stays on the guarded HTTP client (D-1, D-11).
